# プロダクトビジョン

AI Office は、人間が定義した仕事を AI 社員が担当工程ごとに処理できる汎用基盤である。人間は目的、受け入れ基準、実行範囲と権限の限界を定め、システムはその範囲内の作業と結果を忠実に実行・記録する。

## 製品の独立性と最初の完成目標

**AI Officeは、OpenClawやCodexなどの外部AIエージェントを必須としない独立したアプリケーションである。** AI Provider、Python、Git、GitHub CLI、隔離環境などの明示された基盤依存は許されるが、外部AIエージェントが内部のRun Input、ソースハッシュ、作業引継ぎを生成することを製品の成立条件にしない。

最初の完成目標は小規模Python修正とする。利用者がGitHub Issueとリポジトリを指定し、AI OfficeがIssueの内容と設定から権限・有限予算の案を提示する。人間が固定base・最大読取範囲・Provider送信範囲・最大変更範囲と実行予算を事前承認した後、AI社員がその範囲内で有限の追加調査を行い、原因仮説・具体的な修正対象を選ぶ。AI Officeは固定Run Inputを内部構成し、既存Workflowで生成・隔離検証・独立レビュー・有限改訂を進める。別のGitHub書込み承認を得てDraft PR、CI、証跡を提示する。最終mergeは人間が判断する。

利用者が判断するのは目的、受け入れ条件、許可範囲、外部副作用であり、JSON転記やSHA-256計算ではない。現在の機能と未達事項は[製品機能マップ](product-capabilities.md)に集約する。

## 最優先原則：業務非依存・設定駆動

**AI Office の Python 実行エンジンに、特定の業務専用の機能・処理手順を実装してはならない。**
技術調査、記事執筆などの業務は設定ファイルと実行時入力で定義し、**業務が増えても共通エンジンのソースコードを変更せずに**実行できることを目指す。

- **Workflow 定義（設定ファイル）**：担当ステップ、順序、受け渡し、許可する分岐・有限の反復条件、成果物やレビューの要件を宣言する。各 Step がモデルを選び、Workflow 共通の任意のDestination既定値と、必要なStep別Destination上書きを持つ。**独立レビュー担当の人数・順序・専門分野も Workflow/Employee の設定で宣言する**。共通エンジンはレビュー担当の人数を知らず、宣言された有限集合をそのまま実行する。1人でも複数人でも、人数を変えるための Python 改修を要しない。
- **Employee 定義（設定ファイル）**：AI 社員の再利用可能な専門能力・行動原則、役割、使用を許されたツールを宣言する。接続先やモデル選択は持たない。同じ職能を複数 Workflow で使う場合、その共通指示は Employee に置き、Workflow へ重複させない。
- **Run Input**：個別の依頼内容・テーマ・事実・証拠・受け入れ基準を渡す。依頼ごとの内容を共通コードや再利用可能な Workflow / Employee 定義へ埋め込まない。
- **共通エンジン（Python）**：設定の検証・安全な解釈、実行・状態遷移、権限と有限予算の強制、失敗時の停止、Run/Manifest・Evidence・Artifact の保存と整合性を担う。特定の Workflow 名、Employee 名、業務名や固定アクション列を知る必要があってはならない。

この分担では、Employee は「どのような汎用職能で考え処理するか」、Workflow は「この業務の手順・引継ぎ・出力/判定契約」、Run Input は「今回の具体的な要求と根拠」、Engine は「認可・試行上限・スナップショット・証跡をどう機械的に保証するか」を所有する。AI の指示はエンジンの安全保証を代替しない。

**禁止する設計**：業務固有の Workflow/Employee ID、固定ステップ列、レビュー内容、レビュー担当の人数・順序・判定組み合わせ、修正回数を Python の実行分岐・認可条件・進行条件にハードコードすること。業務別の新エンジン、重複する承認・永続化機構、不要な Phase/adapter/wrapper を増やすことも避ける。既存コードに業務専用の分岐がある場合、その存在を将来の正しい汎用設計の根拠にせず、既存共通機構への統合・簡素化を優先する。

**設定で何でも実行できるという意味ではない。** 設定で表現できる条件・反復は明示的、検証可能かつ有限とし、各 Run の定義・入力・承認範囲・上限を固定する。権限の拡大、恣意的なコード実行、自動 retry/fallback/recovery、公開などの副作用を設定や AI の判断で暗黙に許可しない。未対応の設定は実行前に拒否し、不明な結果は安全に停止する。

この原則は今後も守る設計・受け入れ基準である。有限のbounded Job、独立Reviewer、改訂は実装済みだが、Issueからの自律調査やRun Input準備まで完成しているわけではない。現在の実装と目標との差は[製品機能マップ](product-capabilities.md)、実装経緯は[Current Architecture](architecture.md)、個別変更はGitHub Issueで管理する。

## 提供する価値

- テキストで定義した社員と仕事を追加・変更できる。
- 共通基盤が状態遷移、入力検証、成果物保存、および再試行の可否・承認・履歴を一貫して扱う。再試行は暗黙には行わない。
- 実行に使った定義・入力・プロンプト・生応答・成果物・イベントを追跡できる。
- AI 社員が作成した成果物を、設定で宣言した**任意の正の有限人数**の独立した AI セッションで元の要求に照らしてレビューし、根拠のある指摘を作成工程へ戻して改訂・再レビューできる。全担当の合格（全員 PASS）がそろって初めて人間受け入れ候補とし、1人の修正要求が他の担当の合格で打ち消されない。成果物と指摘は管理されたワークフローで受け渡し、人間が AI 間でコピー＆ペーストする手間を減らす。受け入れや公開などの判断権限は人間に残す。人数・専門分野は設定の責務であり、エンジンは業務や人数を知らない。
- 長期的には、人間が一度仕事を割り当て、品質基準と有限の認可・安全範囲を事前に定めることで、AI Office が作成・独立レビュー・改訂・再レビューを自律的に進め、基準を満たす候補または理由を伴う安全な停止を提示する。人間は定型的な引継ぎを逐次調整するのではなく、例外を判断し、最終受け入れと公開・mergeを担う。これは製品の将来方針であり、現在の実装状況を示すものではない。
- 仕様を GitHub Issue で管理し、AI が再現可能な開発作業を行える。

## 守る原則

- 人間が仕事の目的、受け入れ基準、対象範囲、有限の実行上限と許可する効果を定める。将来の明示的な opt-in 自律ジョブは、この認可範囲内でのみ定義済みの作成・レビュー・改訂工程を進める。
- AI は割り当てられた工程と権限の範囲だけを処理する。自己判断で workflow、認可方針、上限を広げたり変更したりしない。
- 定義・認可範囲にない工程、分岐、補完は行わない。
- 不正な定義は実行開始前に失敗させる。
- Business、Execution、Publication、Recovery の権限は目的別に扱う。将来の upfront authorization は「承認なし」ではなく、範囲と上限を明示した別の認可モデルであり、各外部実行の前に機械的に検証する。現在の一回ごとの承認保証を弱めるものではなく、実装には別途セキュリティ設計が必要である。
- provider、外部公開、回復・再試行などの副作用は、それぞれの明示された権限なしに実行しない。Artifact が品質基準を満たしても、それだけで公開や merge を許可しない。
- 上限、証跡、費用または結果が不明・矛盾する場合は、自律進行を停止して理由と保持された作業を人間に提示する。
- 障害や再起動後は保存済みの状態と証跡から判断し、不明な状態を推測で進めない。
- 決定性、監査可能性、制御可能性を維持しながら、同じ保証をより単純な構造で実現できる場合は単純な構造を優先する。

## 非目標

この段階では業務別専用Engine、無制限agent loop、並列実行、GUI、外部エージェント連携、PR自動mergeを中核要件としない。有限のbounded Artifact Jobは実装済みだが、Issue受付・自律調査・Run Input自動準備は未完成である。追加時は既存構造の再利用と簡素化を優先し、明示的な状態遷移・認可・監査を維持する。
